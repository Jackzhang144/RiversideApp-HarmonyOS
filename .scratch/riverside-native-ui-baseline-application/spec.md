# RiverSide 原生 UI 基线应用

Status: ready-for-agent

## Problem Statement

RiverSide 已有一个在 API 23 模拟器上反复评审的 HDS + ArkUI 原生 UI/UX 原型，也已有可工作的论坛浏览、认证与 Reply MVP。原型包含更完整的五 Tab 产品方向和大量静态 Fixture，而正式页面仍使用较简陋的结构；如果直接复制原型，会把聊天、消息、搜索、发起 Topic、个人中心扩展和附件等尚未实现的能力伪装成正式功能，并破坏现有分页、缓存、认证与 Reply 恢复语义。

用户需要把已经确认的原生视觉基线应用到正式页面，同时清楚区分真实能力、无响应占位和长期保留的原型实验区。迁移必须保持现有 RiverSide/Discourse 契约与业务状态，不以静态 Fixture 代替真实数据，也不能让 UI 基线工作顺带扩大功能范围。

## Solution

将原型中已经确认的 HDS 悬浮导航、系统 Symbol、页面层级、卡片、间距、状态反馈和 Reply 编辑体验迁移到现有正式流程。正式根导航显示首页、Category、聊天、消息、我的五个 Tab，其中首页、Category、我的是可用入口，聊天和消息是明确不可用的未来能力占位。

Home、Category、Topic/Post、账户认证和 Reply 继续使用现有真实数据、页面状态、缓存、分页、会话和不确定提交恢复模型。尚未实现的功能以一致的视觉降级、无响应和无障碍“未实现”语义呈现，不创建空白页面或虚假业务状态。

原型不退役，而是作为长期 UI 实验区通过“我的”页悬浮胶囊入口保留。后续 UI 变化先在原型中实验，只有经过用户明确确认并形成独立规格或 Ticket 后，才迁移到正式页面并重新接入真实契约。

## User Stories

1. 作为 RiverSide 用户，我想看到 HarmonyOS 原生的页面层级与反馈，以便应用符合系统使用习惯。
2. 作为 RiverSide 用户，我想在底部看到首页、Category、聊天、消息和我的五个产品入口，以便理解应用的整体产品方向。
3. 作为 RiverSide 用户，我想让首页、Category 和我的正常切换，以便使用已经具备真实闭环的能力。
4. 作为 RiverSide 用户，我想让聊天和消息明确显示为“未实现”，以便不会误以为它们已经可用。
5. 作为 RiverSide 用户，我点击聊天或消息时不希望进入空白页或看到虚假内容，以便应用不会伪装尚未交付的能力。
6. 作为无障碍用户，我想让聊天和消息被读作“未实现”，以便我能理解它们当前不可用。
7. 作为 RiverSide 用户，我不希望通过根页面左右滑动误入聊天或消息，以便根导航状态始终可预测。
8. 作为 RiverSide 用户，我想在底部导航中看到系统 Symbol、悬浮材质和正确的安全区避让，以便获得一致的 HDS 原生体验。
9. 作为访客，我想在 Home 看到来自真实服务端的最新回复 Topic，以便浏览社区最新动态。
10. 作为访客，我想在 Home 加载时看到明确反馈，以便知道应用仍在工作。
11. 作为访客，我想区分 Home 空结果和请求失败，以便采取正确的恢复操作。
12. 作为访客，我想下拉刷新最新回复并在刷新失败时保留已有内容，以便短暂网络故障不会清空页面。
13. 作为访客，我想横向滚动 Home 排序页签栏查看全部标签，以便了解未来提供的发现方式。
14. 作为访客，我想让最新发表、未读、热门和精华明确显示为“未实现”且不切换内容，以便不会把静态原型列表误认为真实数据。
15. 作为访客，我想让 Home 根页面不显示无意义的返回按钮，以便导航语义正确。
16. 作为访客，我想看到搜索和发布新 Topic 的未来入口，但明确知道它们尚未实现，以便理解产品方向而不会进入空页面。
17. 作为无障碍用户，我想让搜索和发布新 Topic 入口被读作“未实现”，以便其状态与视觉用户一致。
18. 作为访客，我想浏览真实服务端返回的 Category 层级和排序，以便找到正确的论坛内容。
19. 作为访客，我想让 Category 使用原型确认的 Symbol、间距和列表层级，以便目录更清晰易读。
20. 作为访客，我不想在正式 Category 中看到原型 Fixture 的虚构分组，以便页面只反映真实论坛结构。
21. 作为访客，我想在 Category 缓存命中时先看到旧内容并后台刷新，以便启动体验不被网络等待阻断。
22. 作为访客，我想在 Category 刷新失败时保留缓存内容并获得非阻塞提示，以便仍可继续浏览。
23. 作为访客，我想从 Category 打开真实 Topic 列表，并看到加载、内容、空态、错误和重试，以便路径完整可恢复。
24. 作为访客，我想让 Topic/Post 使用统一卡片、字体、颜色和间距，以便长讨论保持清晰层级。
25. 作为访客，我想继续按现有 Post 顺序和分段加载阅读 Topic，以便 UI 迁移不改变阅读结果。
26. 作为访客，我想在追加 Post 失败时保留已经读取的 Post 并重试，以便阅读位置不会丢失。
27. 作为访客，我不想看到没有真实倒序能力支撑的“最早/最新”排序控件，以便页面没有虚假交互。
28. 作为用户，我想在 Topic 已关闭或归档时看到不可 Reply 的真实限制，以便不会尝试无效操作。
29. 作为未登录用户，我想在“我的”页看到登录入口和明确的会话状态，以便知道如何获得写入权限。
30. 作为已登录用户，我想看到“已登录 RiverSide”和会话已安全保存的信息，以便确认认证状态。
31. 作为用户，我不想在“我的”页看到 Fixture 昵称、头像、校友身份或认证徽章，以便应用不展示无法由会话证明的个人资料。
32. 作为用户，我想让个人信息、RSC 钱包、我的 Topic、我的 Reply、我的草稿、我的书签、应用设置和关于 RiverSide 始终显示为“未实现”占位，以便了解未来规划。
33. 作为用户，我点击“我的”页占位项时不希望发生页面跳转或提示，以便不会进入没有业务能力的页面。
34. 作为无障碍用户，我想让“我的”页每个占位项都读出“未实现”，以便准确理解可用范围。
35. 作为用户，我想在会话恢复或退出过程中仍能看到完整“我的”页面和原型入口，以便认证忙碌状态不会遮盖其他内容。
36. 作为用户，我想让登录和退出登录成为本轮“我的”页唯二真实账户操作，以便功能范围清晰。
37. 作为已登录用户，我想对 Topic 或指定 Post 编写纯文本或 Discourse Markdown Reply，以便参与讨论。
38. 作为 Reply 作者，我想看到实时字符数和草稿仅保存在当前进程的提示，以便理解输入状态。
39. 作为 Reply 作者，我不想被原型中未经服务端证明的 1000 字上限阻止，以便正式编辑器遵循真实契约。
40. 作为 Reply 作者，我想让图片和 @提及图标明确显示为“未实现”且无响应，以便不会误以为附件或提及已经支持。
41. 作为 Reply 作者，我想在提交、结果确认、失败和重新认证过程中保留草稿，以便不会因异常丢失输入。
42. 作为 Reply 作者，我想让不确定的提交先确认服务端结果且绝不自动重发，以便避免重复 Reply。
43. 作为 Reply 作者，我想在成功或失败时得到一致的 HDS SnackBar 反馈，以便清楚知道结果。
44. 作为产品设计者，我想从“我的”页随时进入 UI 原型，以便继续实验后续界面方向。
45. 作为产品设计者，我想让原型入口在未登录、会话恢复和已登录状态下始终可见，以便实验不依赖账户状态。
46. 作为产品设计者，我想让原型入口使用避让底部导航与安全区的悬浮胶囊样式，以便它与原型控制入口保持一致。
47. 作为产品设计者，我想保留原型 Fixture、页面状态控制和系统通知测试，以便后续 UI 迭代可以先在隔离环境中评审。
48. 作为正式应用用户，我不希望原型系统通知测试变成正式消息能力，以便测试权限与产品行为保持隔离。
49. 作为维护者，我想让原型变化只有在用户明确确认后才进入正式 UI，以便实验不会意外改变产品行为。
50. 作为维护者，我想让每次原型晋升通过独立规格或 Ticket 重新接入真实数据和状态，以便正式页面不会依赖 Fixture。
51. 作为维护者，我想继续使用单一 AppShell 管理导航和 Authenticated Session，以便 UI 迁移不分裂全局状态所有权。
52. 作为维护者，我想继续让只有 HTTP 401 触发全局会话失效，以便普通网络或解析错误不会错误登出用户。
53. 作为维护者，我想让新增 ArkTS 代码保持完整静态类型且不使用 `any`，以便编译器可以验证边界。
54. 作为维护者，我想让每个页面迁移独立验证和提交，以便变更可审查、可定位且不混入业务扩展。
55. 作为验收者，我想区分模拟器结构回归与 API 23 真机视觉验收，以便不会把模拟器结果误认为 HDS 最终证据。

## Implementation Decisions

- 使用 ArkTS + ArkUI，遵循强化静态类型约束，不引入 `any`，对空值、接口结果、错误和页面状态显式建模。
- HDS 优先，实际采用的组件和属性必须确认 API 23、Stage 模型、Phone 与中国大陆发行约束；HDS 不覆盖或无法满足语义时使用 ArkUI 基础组件。
- 正式根导航采用真正的根级 HdsTabs 悬浮栏，复用原型确认的系统 Symbol、悬浮材质、底部安全区与手持适配方向；不得手绘底栏。
- 根导航显示 Home、Category、Chat、Notifications 和 Account。只有 Home、Category 和 Account 是可选目的地；Chat 和 Notifications 是视觉降级、无选中态、无响应且无障碍标注“未实现”的占位。
- 禁止根内容左右滑动切换。Home 的排序标签栏可以横向滚动展示全部标签，但内容区不能通过点击或滑动进入未实现排序。
- Topic、认证和 Reply 保持二级导航关系；Home 是根页面，不显示返回操作。
- AppShell 继续统一持有根导航、二级导航和 Authenticated Session。页面不直接访问 HUKS、ArkWeb 或 HTTP。
- ForumRepository、AuthRepository 与统一 HTTP 客户端的职责保持不变。UI 迁移不得修改 RiverSide/Discourse 服务端契约。
- Home 的 Latest Replies 使用现有真实加载模型、错误恢复和下拉刷新。Latest Created、Unread、Hot 和 Featured 只作为“未实现”标签显示，后续通过独立功能 Ticket 接入已知服务端契约。
- Home 的 Search 和 New Topic 图标保留为无响应占位，不创建目的地、状态模型或 API 调用。
- Home Topic 使用原型确认的卡片结构：作者与更新时间、右上状态、独立标题和摘要、Category 标签、Reply 与浏览统计；字段必须来自真实 Topic 模型。
- Category 采用原型的系统 Symbol、列表层级、间距和视觉分组方式，但分组、排序、缓存和内容必须来自真实 Category 树。禁止迁移 Fixture 名称与 Fixture 分组。
- Topic/Post 采用与 Home 一致的卡片、字体、颜色和间距，继续使用现有详情、Post 窗口、追加加载、关闭/归档限制与错误恢复。
- 不迁移 Topic 原型的 Earliest/Latest Reply 排序控件，不新增倒序加载或跳转语义。
- Account 头部只显示通用系统头像、当前认证状态和本地会话安全状态，不新增资料接口，也不使用 Fixture 身份内容。
- Account 始终展示八个非交互占位：Personal Information、RSC Wallet、My Topics、My Replies、My Drafts、My Bookmarks、App Settings、About RiverSide。每项必须视觉降级、可见标注“未实现”，且无障碍文案包含“未实现”。
- Account 的占位和原型胶囊不受认证状态影响。会话恢复和退出只锁定相关账户操作，不以全屏状态替换整个 Account 页面。
- Reply 保持纯文本或 Discourse Markdown 源文本契约，继续执行 trim、空输入阻止、会话失效草稿保留和不确定提交确认。
- Reply 显示实时字符数与内存草稿提示，不设置原型的 1000 字硬限制。
- Reply 的 Image 和 Mention 图标是无响应的“未实现”占位，不新增附件、上传或提及接口。
- 页面状态不使用原型统一状态开关。正式状态矩阵为：

  | 页面/能力 | 正式状态 |
  | --- | --- |
  | Home Latest Replies | initial、loading、content、empty、error、refreshing；刷新失败保留内容。 |
  | Home 其他排序 | unavailable 占位，不切换内容。 |
  | Category | initial、loading、cached content、background refreshing、empty、error；刷新失败保留缓存。 |
  | Category Topic 列表 | initial、loading、content、empty、error、retry。 |
  | Topic/Post | initial、loading、content、empty、error、loading more、pagination error；追加失败保留 Post；关闭/归档限制 Reply。 |
  | Account | restoring session、signed out、authorization error、signed in、signing out；占位和原型入口始终可见。 |
  | Reply | closed、editing、submitting、checking、error、reauthenticate、success；失败保留草稿。 |
  | Chat/Notifications | unavailable 占位，无正式页面状态。 |
  | System notification | 无正式状态，只存在于原型。 |

- 401 继续由 AppShell 统一处理；其他 HTTP、解析和网络错误保留为页面级错误，不为每页强造 unauthorized 页面。
- 原型作为持久 UI 实验区保留，不执行原型退役。Account 中的悬浮胶囊入口始终可见并避让根悬浮栏与底部安全区。
- 原型中的 Fixture、状态控制与系统通知测试保持隔离。系统通知不进入正式 Notifications 能力。
- 本规格不新增 Debug/Release 条件分支；原型入口的 Release 可见性留给后续独立决策，当前迁移保持现有构建暴露方式。
- 原型变化不得自动同步正式页面。每次晋升必须先获得用户明确确认，再以独立规格或 Ticket 迁移。
- 复用统一 token、页面容器、状态组件和无障碍文案规范；页面迁移按可独立验证的小步完成，不混入业务重构。
- 不修改、暂存或提交本地签名配置。

## Testing Decisions

- 自动化测试只验证外部可见状态、导航结果、请求语义和恢复行为，不断言 ArkUI Builder 内部结构、私有字段或具体组件树实现。
- 采用现有 AppShellModel 依赖组合边界作为唯一最高层自动化行为接缝。通过替换 ForumRepository、认证运行时和系统能力依赖，观察用户可见状态与流程。
- 不为单个页面新增低层 mock 接缝。纯视觉结构通过构建、设备交互和人工视觉验收覆盖。
- 根导航测试覆盖：Home、Category、Account 可切换；Chat、Notifications 点击无选中、无跳转、无提示；根内容滑动不能进入占位页。
- Home 测试覆盖：Latest Replies 加载、内容、空态、错误、重试、下拉刷新和刷新失败保留内容；四个未实现排序不触发加载或改变内容；搜索和发布占位不产生导航或请求。
- Category 测试沿用现有浏览与缓存先例，覆盖真实层级、缓存命中、后台刷新、空态、首屏错误、刷新失败保留缓存和 Category Topic 跳转。
- Topic/Post 测试沿用现有 Topic reading 先例，覆盖详情、初始 Post、追加窗口、追加失败保留内容、重试、关闭/归档 Reply 限制，并证明不存在原型排序行为。
- Account 测试覆盖未登录、恢复中、已登录、退出中和授权错误；每个状态都保持八个占位和原型胶囊可见；只有登录/退出产生账户动作。
- 占位测试按用户可见行为验证：标注“未实现”、无选中态、无导航、无业务请求、无反馈，并提供对应无障碍描述。
- Reply 测试沿用现有 Reply boundary 与 recovery 先例，覆盖空输入阻止、成功、明确拒绝、401、网络中断、超时确认、显式重试、草稿保留，以及长于 1000 字的输入不被客户端原型限制截断。
- 原型隔离测试证明 Fixture 和系统通知测试只能从原型入口访问，不会出现在正式 Home、Category、Notifications、Account 业务区域。
- ArkTS 编译、类型检查和现有设备测试必须通过；不得因 UI 迁移降低现有测试数量或跳过失败。
- API 23 模拟器验证信息结构、五 Tab 基础交互、占位无响应、页面状态、导航、下拉刷新和 Reply 编辑器基础键盘路径。
- API 23 中国大陆物理真机验证 HDS 悬浮材质、Symbol、触控反馈、安全区、软键盘、动效和无障碍体验。模拟器截图不作为沉浸视觉通过证据。
- 每个实施 Ticket 在提交前执行与其风险匹配的最小验证；最终执行完整 API 23 回归并记录模拟器与真机证据边界。

## Out of Scope

- 实现 Chat 或 Notifications 页面、后端契约、搜索、消息同步、私信或频道能力。
- 实现 Latest Created、Unread、Hot 或 Featured 的真实 Home 数据加载、分页和认证语义。
- 实现搜索、发布新 Topic、图片或附件上传、@提及、表情、富文本工具栏、反应、投票或后台任务。
- 实现 Personal Information、RSC Wallet、My Topics、My Replies、My Drafts、My Bookmarks、App Settings 或 About RiverSide。
- 新增用户资料、头像、校友身份、认证徽章或个人中心接口。
- 将原型系统通知测试升级为正式系统通知、推送或 Notifications 产品能力。
- 删除原型、Fixture、原型状态控制、原型入口或原型系统通知测试。
- 决定原型入口是否应从 Release 构建隐藏。
- 修改 RiverSide/Discourse 服务端、认证协议、缓存策略、分页契约或 Reply 安全恢复策略。
- 像素级复刻 Flutter、品牌重塑或一次性完成全局视觉精修。
- 使用模拟器结果宣称 HDS 沉浸材质、真实软键盘、触控、动效或物理真机行为已经验收。
- 修改或提交本地签名配置。

## Further Notes
